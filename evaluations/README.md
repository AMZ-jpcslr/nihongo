# 検証の記録

nihongoは、ルールを1つ変えるたびに、変える前の版と目隠しで比べて、良くなった時だけ採用しています。この文書は、その記録です。

## 比べ方

- 同じ原文と依頼を、比べる版ごとに別々のAIに渡して直させます。それぞれのAIは自分の版のスキルしか読めません。
- 出来上がった2つの文をXとYに並べ替え、どちらがどの版かを伏せて判定します。XとYの割り当ては課題ごとにランダムです。
- 判定は、作者が読み比べる方法と、別のAIに判定させる方法の2つを使いました。別のAIに判定させる時は、課題ごとに「変わってはいけない点」の一覧を渡し、1つでも崩れた案は、読みやすくても負けにしています。
- 判定では、次の3つを分けて見ます。
  - 自然さ：読み手、載る場所、文書の役割に合っているか
  - 意味の保持：誰が何をするか、期限、条件、否定、数値、要求の強さ、確かさが変わっていないか
  - 直す深さ：直すべき所を直し、直さなくていい所に手を入れていないか

課題の原文は `tasks/` に置いてあります。どれもAIが書いた合成の文章です。

## 結果

### 推敲の比較（作者が判定）

AIが書いた原文を直す課題で、nihongoと、推敲用に作られた別の公開スキルを比べました。

| 回 | 課題 | nihongoが自然だった数 |
|---|---|---|
| 1 | 新しく書く8題（LINE、ビジネスチャット、謝罪文、技術ドキュメントなど） | 8 / 8 |
| 2 | 直す7題 | 7 / 7 |
| 3 | 意地悪な4題（長文、崩れた原文、5人への書き分け、情報の多いお知らせ） | 4 / 4 |
| 4 | 直す7題（相手のスキルを最新版にして再実施、`tasks/rewrite/`） | 7 / 7 |

### 意味の保持（別のAIが判定）

条件、否定、程度、時系列、対象の範囲、誰が何をするかを、わざと入れた業務文書3題（`tasks/meaning/`）で確認しました。31項目のうち、事実や求める行動が変わった所はありませんでした。

### ルールを足した時の比較（作者が判定）

足そうとしたルールの多くは、変える前の版に勝てませんでした。勝てなかったものは入れていません。

| 足そうとしたルール | 結果（新しい版の勝ち-負け） | 採用 |
|---|---|---|
| 発話意図と文末を保つ | 3-3（1題は同じ文） | しない |
| 上に、文末をそろえてよい場合の補足を足す | 0-4 | しない |
| 2つをまとめた「発話意図と自然さの両立」 | 2-5 | しない |
| 前後のつながりを確かめる | 3-4 | しない |
| 情報の順番とまとまりを確かめる | 3-4 | しない |
| 句点と文章全体のリズム（合成の例文つき） | 5-2 | する |

ルールの文だけを足した版はどれも勝てず、例文を付けた版で初めて勝ちました。

### 技術文書の強化（別のAIが判定）

README、API仕様、障害報告、設計メモ、PR、論文の要旨、運用手順などで、強化前の版と比べました。

- 強化前の版との比較：3回で15勝1敗3分け。意味が崩れたのは強化前の版だけで6回。
- スキルを使わないAIとの比較（最新のv12）：16勝10敗2分け。新しく作った課題だけでは7勝5敗。
- 推敲用に作られた別の公開スキルとの比較：21勝3敗4分け。

詳しくは `technical.md` にあります。スキルを使わないAIには、強化した直後の版が一度負けていて、そこから直した経緯も載せています。

## 気をつけてほしいこと

- 作者が判定した回は、判定者が1人です。
- 直すAIも判定するAIも、同じ会社のモデル（Claude）を使っています。
- 課題の数は、1回あたり4〜16題です。
- 同じ依頼でも、AIは毎回まったく同じ文を書くわけではありません。数字は目安として見てください。
